# فحص الصور ومراقبة المحتوى في Kenza Hub

**الحالة:** تصميم تقني مبدئي معتمد للعمل عليه — لا يوجد تكامل فعلي مفعّل، ولا صور أعضاء تُرسل إلى Google في هذه المرحلة.

## 1) ربط التصميم بقاعدة البيانات الحالية

راجع [تقرير مطابقة التصميم مع مخطط Supabase الفعلي](./schema-alignment.md) لمعرفة حالة الـ bucket الحالي، وسياسات الرفع، ومسار الرفع في Flutter، وتصميم الحجر الخاص وربط الموافقة بالجداول الحالية. هذا التقرير مبني على فحص قراءة فقط، ولا ينفذ تغييرات.

## 2) الهدف والنطاق

فحص كل صورة يرفعها أي عضو إلى Kenza Hub قبل إتاحتها للآخرين، وليس صور المنتجات فقط. يشمل النطاق:
- صور المنتجات وصور المعرض التابعة لها.
- صور الحساب/الملف الشخصي.
- أي نوع آخر من الصور يضيفه التطبيق لاحقاً.

يجب تحديد نوع الصورة والغرض منها قبل تقييم الجودة والملاءمة؛ معايير صورة المنتج تختلف عن صورة الحساب.

## 3) دور Gemini

يُستخدم Gemini عبر طبقة خادم آمنة لتحليل الصورة بصرياً وإرجاع نتيجة منظمة، وليس لاتخاذ قرار حر غير قابل للمراجعة.

المهام:
1. **ملاءمة الصورة:** هل تحتوي على منتج/شخص/محتوى متوقع لنوع موضع الرفع؟
2. **مطابقة القسم:** بالنسبة لصورة المنتج، هل الصورة مرتبطة بالقسم والتصنيف المختارين؟
3. **المحتوى المخالف:** اكتشاف العري والمحتوى الجنسي أو الخادش، والعنف والدماء والمحتوى الصادم، والمواد المحظورة وفق سياسة Kenza Hub.
4. **مؤشرات الجودة:** وصف الضبابية، ضعف الإضاءة، القص غير المناسب، صغر المنتج أو عدم ظهوره بوضوح، والكتابة/العلامات المائية المشتتة.
5. **إشارات الاحتيال أو التضليل:** مثل صورة لا تبدو مرتبطة بالمنتج المعلن أو صورة ترويجية خارجية بدلاً من صورة السلعة.

لا يُطلب من Gemini تحديد هوية الأشخاص أو استنتاج صفاتهم الحساسة. وجود وجه بشري في صورة الحساب ليس مخالفة بحد ذاته.

## 4) فصل السلامة عن جودة الصورة

لا ينبغي رفض صورة لمجرد أن جودتها ضعيفة إذا لم تكن مخالفة. نحتفظ بنتيجتين منفصلتين:

- **Safety / Policy:** هل المحتوى مسموح وفق سياسة المنصة؟
- **Quality / Relevance:** هل الصورة واضحة ومناسبة لموضع الرفع؟

أمثلة:
- محتوى محظور بوضوح: رفض.
- صورة آمنة لكنها ضبابية: طلب إعادة رفع/تحسين، دون تصنيفها كمخالفة.
- نتيجة غير مؤكدة أو تصنيف متضارب: مراجعة بشرية.
- صورة آمنة وواضحة وملائمة: قبول.

## 5) حالات القرار

الحالات النهائية المقترحة:
- `approved`: اجتازت فحص السلامة والملاءمة والجودة المطلوبة.
- `rejected`: توجد مخالفة واضحة وفق سياسة مكتوبة.
- `needs_review`: ثقة منخفضة، تعارض بين الفحوص، أو حالة حساسة تحتاج مراجعة.
- `needs_better_image`: الصورة مسموحة لكن جودتها لا تحقق الحد الأدنى.
- `processing`: الفحص جارٍ.
- `failed`: تعذر الفحص تقنياً؛ لا يعني أن الصورة آمنة ولا يسمح بنشرها.

**قاعدة النشر:** لا تظهر أي صورة للعامة قبل حالة `approved`. في حالة تعطل Gemini أو انتهاء المهلة، تبقى الصورة معلقة ولا يتم تجاوز الفحص تلقائياً.

## 6) خط سير رفع الصورة

1. يختار العضو الصورة ويحدد موضعها: منتج، صورة حساب، أو نوع آخر.
2. يتحقق التطبيق من الامتداد والحجم والأبعاد الأساسية، ثم يعرض معاينة.
3. تُحفظ الصورة في مساحة/مسار غير عام أو في حالة حجر (quarantine) لا يمكن للجمهور الوصول إليها.
4. يرسل الخادم الصورة إلى Gemini بعد التحقق من هوية صاحب الطلب وصلاحياته ونوع الصورة.
5. يستقبل الخادم استجابة منظمة تشمل مؤشرات السياسة والجودة والملاءمة وسبباً مختصراً.
6. تطبق قواعد Kenza Hub الحتمية على النتيجة؛ لا يُترك قرار النشر لنص حر من النموذج.
7. إذا قُبلت، تُنقل/تُفعّل الصورة في مسارها النهائي. إذا رُفضت أو احتاجت مراجعة، تظل غير عامة.
8. يستطيع العضو رؤية سبب مفهوم وإعادة رفع صورة بديلة.
9. تسجل النتيجة والإصدار وقواعد القرار دون تخزين الصورة داخل سجلات النظام.

يجب أن يكون نقل الصورة إلى المسار العام خطوة لاحقة للفحص، وليس سابقاً له. تفاصيل الربط مع Storage والجداول الحالية تُحسم بعد مراجعة مخطط الصور الفعلي في Supabase؛ لا نفترض أسماء جداول أو سياسات غير متحققة.

## 7) سياسة القرار المقترحة

### أ. مخالفة واضحة
- رفض مباشر عند ثبوت محتوى محظور بوضوح.
- حفظ رمز سبب داخلي، ورسالة عربية مناسبة للعضو.
- عدم عرض الصورة في أي صفحة عامة أو نتائج بحث.

### ب. اشتباه أو تضارب
- إحالة إلى `needs_review`.
- لا يتم نشر الصورة حتى انتهاء المراجعة.
- لا يُرسل للعضو وصف تفصيلي حساس للمحتوى؛ تظهر رسالة عامة مناسبة.

### ج. جودة ضعيفة
- تنبيه العضو إلى المشكلة المحددة: ضبابية، إضاءة، قص، أو عدم ظهور المنتج.
- السماح بإعادة الرفع.
- لا يُسجل ذلك كمخالفة سلوكية على حساب العضو.

### د. حالات خاصة
- لا تُصنف صور الملابس العادية أو صور عرض المنتجات تلقائياً كمحتوى خادش لمجرد وجود جسم/عارض أو ملابس مكشوفة نسبياً؛ تُطبق سياسة واضحة بحسب نوع المنتج والسياق.
- صور الملابس الداخلية أو ملابس السباحة تحتاج قواعد معلنة بحسب سياسة الأقسام التي يعتمدها مالك المنصة.
- الصور الطبية أو التعليمية لا تُرفض آلياً لمجرد وجود تصنيف طبي؛ تُراجع حسب السياق والسياسة.
- صور الأطفال تتطلب عتبة حماية شديدة التحفظ؛ أي اشتباه بمحتوى استغلالي أو جنسي يمنع النشر ويصعّد وفق إجراءات حماية ومراجعة مناسبة.
- صور الحساب لها قواعد مختلفة عن صور المنتج، ولا يُشترط أن تحتوي على منتج.

## 8) شكل الاستجابة من خدمة الفحص

يجب أن تكون استجابة الخادم JSON محددة الحقول، مثال توضيحي غير مربوط بموديل أو API محدد:

```json
{
  "decision": "needs_review",
  "safety": {
    "status": "uncertain",
    "categories": ["adult_content"],
    "confidence": 0.61
  },
  "quality": {
    "status": "acceptable",
    "issues": []
  },
  "relevance": {
    "status": "relevant",
    "image_role": "product"
  },
  "reason_code": "SAFETY_UNCERTAIN",
  "member_message_key": "image_under_review"
}
```

- القيم المرسلة من النموذج لا تُعامل كحقائق موثوقة دون تحقق.
- لا نعتمد على confidence وحده؛ يجب معايرة العتبات باستخدام مجموعة صور اختبار ممثلة لفئات Kenza Hub.
- لا نخزن chain-of-thought أو تحليل داخلي مطول؛ نخزن النتيجة المختصرة ورمز السبب فقط.
- لا تُعرض درجة الثقة أو تصنيفات حساسة للمستخدم النهائي.

## 9) طبقة الخادم والأمان

- لا يستدعي تطبيق Flutter Gemini مباشرة ولا يحتوي على API Key.
- استدعاء Gemini يتم من Edge Function/خادم موثوق فقط.
- الأسرار في Secrets server-side فقط.
- التحقق من أن الصورة تخص العضو الذي رفعها ومن أنه يملك صلاحية تعديلها.
- حدود للحجم والامتدادات وعدد الصور ومعدل الطلبات.
- مهلة زمنية، retry محدود، ومنع تكرار نفس مهمة الفحص.
- حماية من إعادة استخدام نتيجة فحص صورة مختلفة؛ تربط النتيجة ببصمة الملف (checksum) ومعرّف الصورة وإصدار السياسة والموديل.
- لا نسجل bytes الصورة أو روابط خاصة أو مفاتيح أو بيانات شخصية في logs.
- لا نسمح بالوصول العام إلى الصور المعلقة أو المرفوضة.
- يجب مراجعة شروط Google وسياسة الاحتفاظ ومعالجة البيانات قبل إرسال صور حقيقية، وإبلاغ الأعضاء بما يلزم في سياسة الخصوصية.

## 10) التخزين وسجل المراجعة — تصميم مبدئي فقط

نحتاج مفهوماً لسجل مراجعة مرتبط بكل صورة، لكن أسماء الجداول والأعمدة النهائية لا تُعتمد قبل فحص مخطط Supabase الكامل.

حقول مفاهيمية محتملة:
- مرجع الصورة ومالكها ونوع استخدامها.
- الحالة الحالية وقرار الفحص.
- رموز أسباب القرار ومؤشرات الجودة/السلامة المختصرة.
- مزود الفحص والموديل وإصداره.
- إصدار سياسة المحتوى المستخدمة.
- وقت الفحص وعدد المحاولات.
- نتيجة المراجعة البشرية (إن وجدت) ومعرّف المشرف ووقت القرار.

لا نحتفظ بنسخة ثانية من الصورة داخل سجل المراجعة. نحتفظ بمرجع آمن فقط، مع سياسة حذف واحتفاظ واضحة.

## 11) لوحة الإدارة

إعدادات مقترحة:
- تشغيل/إيقاف أنواع الفحص حسب نوع الصورة.
- تحديد الأقسام والأنواع المسموح بها.
- حدود الجودة الدنيا.
- مستويات التصعيد إلى المراجعة.
- قائمة أسباب الرفض ورسائلها العربية.
- قائمة انتظار للمراجعات مع صلاحيات مشرف محدودة.
- سجل تدقيق لأي قرار بشري أو تغيير في السياسة.

لا يسمح بتعديل العتبات الحساسة من حساب عادي أو بائع.

## 12) الاختبار قبل التفعيل

نجهز مجموعة اختبار مصنفة يراجعها مالك المنصة، تشمل:
- صور منتجات سليمة وواضحة لكل قسم.
- صور سليمة لكنها منخفضة الجودة.
- صور لا علاقة لها بالقسم.
- صور بها علامات مائية أو أرقام تواصل أو إعلانات.
- صور محتوى جنسي/عري أو عنف أو دماء ضمن بيئة اختبار آمنة ومصرح بها.
- صور حالات حدودية مثل ملابس السباحة/الداخلية والمنتجات الطبية.
- صور حسابات سليمة وصور غير مناسبة لصورة الحساب.
- صور تالفة، امتداد مزيف، حجم زائد، وطلبات متكررة.
- انقطاع Gemini أو تجاوز المهلة أو استجابة غير صالحة.

مقاييس النجاح:
- عدم نشر أي صورة محظورة ضمن مجموعة الاختبار.
- تقليل رفض الصور السليمة خطأً.
- دقة أسباب الرفض وسهولة فهم رسائل العضو.
- عدم نشر أي صورة عند فشل الخدمة.
- عدم إمكانية تجاوز الفحص عبر استدعاء مباشر أو تكرار الطلب.

## 13) علاقة النظام بالبحث بالصورة

الفحص والبحث البصري وظيفتان منفصلتان:
- **فحص الصور:** يقرر هل يسمح بنشر/استخدام الصورة داخل المنصة.
- **البحث بالصورة:** يستخرج embedding لمقارنة صورة البحث بصور المنتجات المعتمدة داخل Kenza Hub.

يمكن مشاركة بعض البنية الخادمية وإدارة المهام، لكن لا نخلط جداول embeddings مع سجل المراجعة أو قرارات السلامة. الصور غير المعتمدة لا تدخل فهرس البحث البصري.

## 14) قرارات وحدود التنفيذ الحالية

- اعتماد Gemini كمحرك تحليل بصري أولي قابل للاستبدال.
- النطاق يشمل كل الصور التي يرفعها الأعضاء، مع قواعد مختلفة حسب نوع الصورة.
- اعتماد الحالات: approved / rejected / needs_review / needs_better_image / processing / failed.
- عدم نشر الصورة قبل قبولها.
- هذا الملف تصميم فقط؛ لا يحتوي على مفتاح API أو اتصال فعلي أو صور اختبار حقيقية.
- لم تُنشأ خدمة Google أو مشروع مدفوع، ولم تُرسل صور أعضاء إلى Google.
- لم تُنفذ migrations أو SQL ولم تتغير قاعدة Supabase.
- لم يُعدل Flutter ولم يُشغّل analyze أو tests أو APK.
- أي تفعيل خارجي أو تكلفة أو إرسال فعلي لصور الأعضاء يحتاج موافقة منفصلة بعد عرض التكلفة وشروط البيانات.
