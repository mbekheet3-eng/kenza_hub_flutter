# البحث بالصورة في Kenza Hub — التصميم المعتمد مبدئياً

**الحالة:** تصميم تقني فقط — لا توجد تغييرات على قاعدة الإنتاج ولا خدمة خارجية منشأة أو مفعّلة.

## 1) نتيجة فحص الوضع الحالي

تمت مراجعة فرع `feature/db-schema-alignment` وقاعدة Supabase الحالية قراءة فقط.

### تطبيق Flutter
- شاشة `lib/screens/search/search_screen.dart` تنفذ البحث النصي والفلاتر والترتيب فقط؛ لا يوجد فيها اختيار صورة أو عرض نتائج بحث بصري.
- حزمة `image_picker` موجودة بالفعل في `pubspec.yaml`.
- `UploadService.pickImage()` يستطيع اختيار صورة واحدة من المعرض أو الكاميرا، مع نسخها إلى مجلد cache.
- `SupabaseService.searchByImage()` متعمد أن يوقف العملية برسالة واضحة؛ لا توجد مطابقة صور فعلية خلفه.
- لذلك لا يجوز إظهار قائمة فارغة أو نتائج البحث النصي على أنها نتائج مطابقة بالصورة.

### قاعدة البيانات
تم التحقق من المخطط الفعلي عبر أدوات Supabase، وليس الاعتماد على ملف `DATABASE_SCHEMA.md` القديم لأنه لا يطابق المخطط الحالي.

- `public.products`: يحتوي `id`, `category_id`, `status_id` وباقي بيانات المنتج.
- `public.product_images`: يحتوي `id`, `product_id`, `image_url`, `display_order`, `created_at`.
- `public.product_statuses`: يحتوي `id` و`slug`، ويرتبط به `products.status_id`.
- RLS مفعّل على الجداول الثلاثة.
- امتداد `vector` متاح على المنصة لكن **غير مثبت حالياً** في قاعدة المشروع.
- لم يظهر مجلد `supabase/` أو migrations ضمن فرع Flutter الحالي.
- قاعدة البيانات الحالية خالية من بيانات المنتجات والصور وفق نتيجة الفحص وقت إعداد هذه الوثيقة.

## 2) شكل التجربة المطلوبة

1. يضغط المستخدم أيقونة الكاميرا في شريط البحث.
2. يختار صورة من المعرض أو يلتقط صورة بالكاميرا.
3. تظهر معاينة للصورة مع خيار استبدالها أو إلغاء البحث.
4. يرسل التطبيق الصورة إلى Edge Function باسم `image-search` عبر HTTPS.
5. تستخرج الخدمة بصمة بصرية (image embedding) من الصورة.
6. تقارن قاعدة البيانات البصمة بصور المنتجات المفهرسة مسبقاً.
7. ترجع النتائج كمنتجات فريدة مرتبة من الأكثر تشابهاً إلى الأقل، مع درجة التشابه.
8. تظهر حالة منفصلة عند عدم وجود تطابق، أو عند فشل الخدمة؛ ولا يتم خلطها مع نتائج البحث النصي.

## 3) المعمارية المقترحة

### أ. Flutter
- استخدام `image_picker` الموجود حالياً.
- التحقق من نوع الملف وحجمه قبل الإرسال، مع حد مقترح 5 MB لصورة البحث.
- عدم رفع صورة البحث إلى bucket أو الاحتفاظ بها بعد انتهاء الطلب؛ تُرسل للمعالجة المؤقتة فقط.
- إنشاء خدمة Flutter مستقلة `ImageSearchService` تستدعي `image-search` وتعيد قائمة معرّفات المنتجات ودرجات التشابه.
- إضافة حالات UI واضحة: اختيار صورة، معاينة، جارٍ البحث، نتائج، لا توجد نتائج، خطأ قابل لإعادة المحاولة.
- جلب بيانات المنتجات من الجداول الحالية باستخدام معرّفات النتائج، مع احترام فلاتر الحالة والتصنيف الحالية.

### ب. Supabase Edge Function
اسم الوظيفة: `image-search`.

مسؤولياتها:
- التحقق من الطلب ونوع الصورة وحجمها، ورفض الملفات غير المدعومة.
- التحقق من هوية المستخدم/سياسة السماح للزائر قبل إتاحة endpoint.
- عدم تسجيل محتوى الصورة أو بيانات اعتماد المزود في logs.
- استدعاء مزود image-embedding خارجي من الخادم فقط.
- تمرير المتجه إلى دالة المطابقة في Postgres.
- إرجاع أقل قدر من البيانات: `product_id`, `similarity`, `matched_image_id`.
- وضع مفاتيح المزود في Edge Function Secrets؛ لا توضع في Flutter أو GitHub أو ملف `.env` متتبع.

### ج. فهرسة صور المنتجات
لا يمكن البحث عن الصور قبل فهرسة صور المنتجات الموجودة في `product_images`.

التدفق المقترح:
1. بعد حفظ المنتج وصوره بنجاح، تُنشأ مهمة فهرسة لكل صورة.
2. عامل/Edge Function يجلب الصورة من Storage، ويولد embedding بنفس الموديل المستخدم في البحث.
3. تُحفظ البصمة وبيانات الموديل وحالة الفهرسة في جدول منفصل.
4. عند استبدال صورة أو حذفها أو حذف المنتج، تُحدّث/تحذف بصمتها تلقائياً.
5. تُتاح إعادة المحاولة للمهام الفاشلة، مع منع تكرار الفهرسة لنفس الصورة والموديل.

## 4) تصميم قاعدة البيانات المقترح

**لا نضيف أعمدة embedding إلى `product_images` مباشرة.** الأفضل جدول منفصل حتى تبقى بيانات الصور الأساسية مستقلة، ويمكن إعادة بناء الفهرس عند تغيير موديل الذكاء الاصطناعي.

الجدول المقترح: `public.product_image_embeddings`

| العمود | الغرض |
|---|---|
| `product_image_id` UUID PK/FK | مرجع لصورة المنتج في `product_images` مع حذف تابع |
| `embedding` `extensions.vector(D)` | البصمة البصرية؛ D هو عدد الأبعاد الذي يحدده الموديل المختار |
| `model_key` TEXT | اسم الموديل/المزود |
| `model_version` TEXT | إصدار الموديل لضمان عدم خلط بصمات غير متوافقة |
| `status` TEXT | pending / ready / failed |
| `attempt_count` INTEGER | عدد محاولات الفهرسة |
| `last_error_code` TEXT NULL | رمز خطأ مختصر، دون بيانات حساسة |
| `created_at`, `updated_at` | التتبع الزمني |

ضوابط التصميم:
- تفعيل RLS على الجدول.
- منع `anon` و`authenticated` من قراءة/إضافة/تعديل/حذف المتجهات مباشرة.
- لا تُرجع دالة المطابقة المتجه نفسه إلى التطبيق.
- دالة المطابقة لا تقبل اسم الموديل أو عدد النتائج دون حدود ثابتة/مسموح بها من الخادم.
- إتاحة التنفيذ لحساب الخدمة فقط، مع منع `PUBLIC` و`anon` و`authenticated` من تنفيذها.
- استخدام HNSW مع cosine distance بعد اعتماد أبعاد الموديل واختبار الأداء.
- لا نضيف `SECURITY DEFINER` لمجرد تجاوز RLS؛ الأفضل أن تستدعي Edge Function الدالة بصلاحية الخدمة، وتكون الدالة محدودة الصلاحيات ومراجعة بعناية.

### دالة المطابقة المقترحة
اسم مبدئي: `match_product_images`.

- تستقبل متجه البحث وعتبة التشابه والحد الأقصى للنتائج.
- تطابق فقط المتجهات ذات `model_key` و`model_version` المعتمدين.
- تستخدم cosine distance (`<=>`) وتحسب التشابه من المسافة.
- تربط النتائج بـ `product_images` ثم `products` و`product_statuses`.
- تستبعد المنتجات غير النشطة/المباعة/المحذوفة وفق قيم الحالة الفعلية المعتمدة.
- تجمع الصور المتعددة للمنتج الواحد بحيث يظهر المنتج مرة واحدة بأعلى درجة تشابه.
- تدعم فلتر التصنيف الاختياري داخل دالة SQL نفسها، قبل ترتيب/تحديد النتائج.

## 5) نقطة يجب حسمها قبل كتابة migration نهائي أو تفعيل الخدمة

لا يمكن تحديد نوع العمود `vector(D)` أو بناء HNSW index صحيح قبل اختيار مزود وموديل صور محدد؛ عدد الأبعاد وإصدار الموديل جزء من توافق البيانات. كما يجب التأكد أن المزود يقدم **image embeddings** فعلية، وليس text embeddings أو مجرد وصف للصورة.

### حالة اختيار مزود embeddings

لم يتم اعتماد مزود أو موديل لاستخراج بصمات البحث البصري حتى الآن. موافقة المستخدم على استخدام Gemini في **مراجعة الصور ومراقبة المحتوى** لا تعني اعتماد Gemini Embedding 2 للبحث البصري؛ فهما استخدامان منفصلان ولهما تقييم تكلفة وخصوصية وأداء مستقل.

يجب أن يقدم أي مرشح للبحث البصري image embeddings فعلية، مع توثيق عدد الأبعاد وإصدار الموديل وإمكانية المقارنة بين صور البحث وصور المنتجات. لا نحدد نوع العمود `vector(D)` أو ننشئ HNSW index قبل اختيار الموديل بعد المقارنة والاختبار.

أي إرسال لصور البحث أو صور المنتجات إلى مزود خارجي يتطلب موافقة صريحة بعد توضيح:
- الصور التي ستُرسل والغرض من الإرسال.
- سياسة الاحتفاظ ومعالجة البيانات لدى المزود.
- التكلفة المتوقعة حسب حجم الاستخدام.
- مكان تخزين مفاتيح API وكيفية حمايتها.

ملاحظة: تصميم فحص الصور ومراجعة المحتوى باستخدام Gemini موثق بشكل مستقل في [docs/image-moderation/README.md](../image-moderation/README.md). لا نخلط بين فحص السلامة/الجودة وبين استخراج embeddings للمطابقة البصرية.

## 6) مراحل التنفيذ والاختبار

1. اعتماد المزود والموديل والأبعاد وسياسة الزائر.
2. إنشاء migration محلية فقط: تثبيت `vector`، جدول البصمات، القيود والفهارس، دالة المطابقة، وRLS/GRANTs.
3. إنشاء Edge Function محلية مع مفاتيح اختبار محلية فقط.
4. اختبار فهرسة صورة منتج، وإعادة المحاولة، وتغيير/حذف الصورة.
5. اختبار مطابقة صورة مماثلة، وصورة غير مرتبطة، وصورة غير صالحة، وحجم زائد، وغياب مفتاح المزود، ومحاولة وصول غير مصرح.
6. ربط شاشة Flutter بالوظيفة وعرض النتائج الفعلية.
7. بناء APK واختباره بعد موافقة المستخدم على تشغيل build.
8. مراجعة مستقلة ثم طلب موافقة منفصلة قبل أي تطبيق على قاعدة الإنتاج أو نشر Edge Function.

## 7) حدود العمل الحالي

- هذه الوثيقة تصميم فقط، وليست migration قابلة للتشغيل.
- لم يتم تشغيل SQL أو تغيير أي جدول/امتداد/سياسة في قاعدة الإنتاج.
- لم يتم إنشاء Edge Function في Supabase أو نشرها.
- لم يتم إنشاء حساب مزود أو خدمة مدفوعة أو إضافة أي secret.
- لم يتم تعديل شاشة البحث أو الادعاء بأن البحث بالصورة يعمل.
